# 新手 Skill 个性化工作流

用户希望把一个现有 Codex／Claude Skill 改得更适合自己的工作方式时，读取本参考。用户不需要理解
Skill 架构，也不需要使用 Requirement Ledger CLI。

## 最少输入

用户唯一必须提供的输入，是一个目标 Skill、它的准确目录，或一条能够准确指向它的
Codex 任务。用户不需要自己诊断缺陷、回忆失败案例，或说明 Skill 应该怎样实现。

绑定目标后，宿主应当：

1. 盘点 Skill 及其直接引用的资源；
2. 按 [Codex 上下文发现](codex-context-discovery.zh-CN.md)查找明确使用或讨论过该 Skill
   且已获授权的任务；
3. 恢复用户可见的纠正、重复摩擦、失败结果、已保留决定，以及看起来已经有效的行为；
4. 建立私有上下文地图，记录每个纳入来源为什么与目标有关；
5. 先给出第一张有证据的改动卡，不要让用户代替程序完成分析。

宿主获准使用当前对话时，当前对话本身可以作为证据。只有在无法有界调取历史、证据不足，
或缺少的答案会实质改变结果时，才请用户补充一个具体失败、需保留的行为或理想示例。每次只问一两个
短问题。不得要求用户选择架构、Schema、测试框架或提示词技术。

## 修改前先解释

生成一张紧凑改动卡：

| 字段 | 必填内容 |
| --- | --- |
| 问题 | 浪费时间、造成错误或体验不对的可观察行为 |
| 证据 | 用户直接说过什么，或提供的失败直接证明什么 |
| 可能层级 | 共享 Skill、当前 Skill、个人偏好或 `unknown` |
| 保留 | 必须保留的有效触发、输出、安全边界和使用习惯 |
| 建议改动 | 最可能有效的最小指令、reference、脚本或测试改动 |
| 验证 | 一个成功案例和一个边界／失败案例 |
| 回滚 | 结果变差时如何恢复旧 Skill |

推断必须标为推断。个人偏好不需要伪装成通用 BUG；它本身就是合理的个性化目标。一次失败不能证明
这是上游问题或通病。

## 授权与实施

- “看看、解释、审查、给方案”必须停在改动卡。
- “修好、实施、开始、开干”只授权已经说明的本地 Skill 改动。
- commit、push、公开发布、市场安装、账号动作和向维护者反馈仍是独立动作。

获得实施授权后：

1. 找到并遵守宿主的 Skill 权威源和仓库规则；
2. 盘点现有触发、分支、脚本、references 和必须保留的行为；
3. 修改最小正确层级，不追加包打天下的万能规则；
4. 校验结构和引用路径；
5. 独立回放成功案例与边界案例；
6. 向用户说明改了什么、改善了什么、还有什么未知；
7. 保留回滚路径，不公开私有证据。

在这条对话式路径中，Requirement Ledger 标准包 CLI 是可选项。只有案例跨多段对话、需要私有证据包，
或需要绑定摘要的前后记录时才使用。

## 完成标准

只有当非专业用户不用阅读 Skill 源码也能回答以下问题时，才算完成：

- 我们修了什么问题？
- 保留了什么有用行为？
- 我的 Skill 具体变了什么？
- 哪个案例现在成功了？
- 什么仍然未知或没有授权？

不能因为 Skill 变得更长、更详细或语气更强，就声称改写成功。
