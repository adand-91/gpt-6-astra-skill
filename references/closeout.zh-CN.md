# 收尾

收尾是账本的后半份工作，也是通常被跳过的那一半。
它的目的是一份用户不必重读整段对话就能相信的报告。

## 回溯到最开始

从本次任务**最早**那条需求开始。不是最近几轮，不是上下文里最新鲜的，
也不是你正好还开着的那些。

这一步的失败是静默的。在长任务里，最前面三条需求恰恰是最可能已被后续工作盖掉、
又最不可能还留在你近期上下文里的。只总结最后两轮就宣布任务完成，
是「假完成」最常见的形态。

如果账本在磁盘上，写报告前先把它读回来，而不是靠记忆重建。

## 每条都要结清

每条账目结成且仅结成四种状态之一。任何一条都不许省略。

| 状态 | 含义 | 还必须写 |
|---|---|---|
| `已完成` | 做出来了，而且验收动作通过 | 产物在哪 |
| `部分完成` | 有一部分能用 | 具体缺的是什么 |
| `明确取消` | 用户明确放弃了 | 什么时候、依据哪条决定 |
| `受阻` | 推不下去 | 在等什么，以及那件事归谁 |

`部分完成` 和 `受阻` 不是需要藏起来的失败。它们恰恰是用户最需要的信息，
把它们埋掉才是让整份报告变得不可信的原因。

## 什么不叫「已完成」

- 启动了一个进程。
- 派出了一个 agent 或子任务。
- 写了方案、设计或脚手架。
- 代码能编译，但验收动作从没跑过。
- 在你的环境里能跑，而确认单写的是另一个环境。

如果确认单里的验收动作没有执行，这条最多是 `部分完成`，
而且报告里要写明是哪个验收动作没跑。

## 拿磁盘核对，不是拿聊天记录核对

报 `已完成` 之前先检查真实产物：文件确实在写明的路径上、命令退出码为零、
输出和确认单承诺的一致。之前对话里说「做完了」是一种声称，不是证据。
聊天记录和文件系统冲突时，以文件系统为准，并把差异报出来。

## 报告的形状

按事项归并，不按时间顺序。收尾报告不是日记。

1. 最初要求的是什么，后来追加了什么。
2. 哪些决定被取代或取消了，被什么取代。
3. 哪些产物真实存在，路径是什么，各自怎么验证的。
4. `部分完成` / `受阻` 项，以及具体缺口。
5. 尚未消除的冲突 —— 文档之间、版本之间，或确认单与现实之间。
6. 唯一的下一个动作。

相关事项合并，保持精炼，不要把对话重新叙述一遍。
标准是：一个完全没参与这个任务的人，能不能照着这份报告动手。

## 交接

如果工作要在另一个对话、另一个 agent 或另一个引擎里继续，那么收尾报告**就是**交接文档。
先写到磁盘，再在聊天里总结它。聊天总结活不过一次上下文重置，文件可以。
