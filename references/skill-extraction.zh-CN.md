# 把重复的活变成 Skill

脚本的 `repeated_commands` 和 `repeated_tool_sequences` 列出了手工做过三遍以上的活。
其中大部分不该做成 Skill。

## 筛子

重复只是触发条件，不是理由。四个问题，按顺序问，第一个「否」就结束：

1. **判断稳定吗？** 每次的决定是同一个，还是取决于会变的上下文？
   `python3 build.py && pytest -q` 是稳定的。「给这份数据挑合适的图表」不是，
   而假装它稳定的 Skill 会理直气壮地做错。
2. **已经有了吗？** 按概念搜，不要按对话里的词搜。相邻 Skill、仓库里的脚本、
   shell 别名、Makefile 目标。两个覆盖同一块地的 Skill，比它们要替掉的手工活更糟。
3. **脚本是不是更合适？** 完全没有判断的，它要的是脚本，不是 Skill。
   一个只说「跑这条命令」的 Skill，每次加载都烧上下文，而且比 `Makefile` 一无所长。
4. **还会再来吗？** 在一个已经结束的项目里出现三次是历史，不是模式。
   跨三个项目出现三次才是模式。

四关全过的，通常是**脚本周围那层判断**，不是脚本本身也不是那段散文：
什么时候跑、输出意味着什么、失败了怎么办。

## 重复其实在告诉你什么

看形状，不只看次数。

- **同一条命令，同一个会话里很多次** —— 通常是缺了一个循环或者反馈回路断了，不是 Skill。
  该问的是它为什么得跑十四遍。
- **同一条命令，跨会话跨项目** —— 真正的候选。
- **重复的工具**序列**（`Write → Bash → Read`）—— 工作流的形状。
  如果某个固定序列反复出现，Skill 要写的是顺序和步骤之间的检查，
  而这恰好是散文擅长、脚本不擅长的东西。
- **同一个话题上反复的纠偏**（来自第 1 步）—— 最强的候选，
  而且是任何命令计数器都找不到的那个。用户不得不把同一件事说三遍，
  说明有一条规则缺失、找不到、或者正在被忽略 —— 写任何东西之前先去
  [mistakes.zh-CN.md](mistakes.zh-CN.md) 对一下层级，
  因为如果是 `规则没触发`，新写的 Skill 一样会被忽略。

## 提案

每个活下来的候选写清：

- **触发** —— 用别人真会用的词汇描述场景，包括对话里出现过的原词。
  用你自己造的词写的触发，永远不会触发。
- **它做什么** —— 步骤，以及判断在哪一步进来。
- **它不许做什么** —— 边界。没有边界的 Skill 会一直长到互相撞车。
- **证据** —— 脚本的计数和引用的纠偏原话。没有证据就没有提案。
- **层级** —— 新 Skill、改已有 Skill、脚本、项目规则，还是什么都不做。
  「什么都不做」是一个合法而且常见的结论；写清为什么。
- **代价** —— 它给每次加载增加了什么，和它省掉的活相比值不值。

## 授权

默认是提案加记录。不创建也不编辑 Skill 文件，不动规则文件，
不修改任何生效 skills 目录下的东西。

收到明确的开干指令，而且只有那时：

1. 确认目标 —— 先复用或扩展，再考虑新建。
2. 写它，触发词汇沿用证据里的原词。
3. 在优化记录里写清改了什么、为什么。
4. 明确写出「怎么知道它起作用了」，以及「什么现象说明它把事情弄糟了」。

没人验证过的生成 Skill，是一个带着触发器的负债。
如果你说不出那个检查是什么，就别发它，直接说出来。

## 优化记录

每轮一个文件，用
[templates/optimization-record.zh-CN.md](../templates/optimization-record.zh-CN.md)。
它的作用是让下一轮能判断上一轮到底有没有帮上忙：改了什么、依据什么证据、
预期是什么，以及 —— 后来补上的 —— 实际发生了什么。

跑了好几轮之后「结果」栏还是空的，那本身就是发现。
它说明改动一直在做但从没被评估过，而这正是规则集越长越不管用的方式。
