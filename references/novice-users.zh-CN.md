# 用户说不清的时候

难的不是「说得含糊」的用户。含糊好办 —— 问就是了。真正难的是两种：
**不知道有哪些选项存在**的用户，和**很自信但要错了**的用户。

这两种从外面看都像是很清楚。而且都不是靠多问几个问题能解决的。

## 他不知道有哪些可能

对一个不知道有什么可选的人问「你想要什么」，你拿到的是一个猜测，
然后你会把这个猜测当成需求。**改成提议而不是提问**：两三个具体选项，
每个的代价用他本来就在用的词说，再加上你的推荐。
问题排序和问法见 [clarify-loop.zh-CN.md](clarify-loop.zh-CN.md)。

判据是他能不能用「行」或者「第二个」回答。如果回答之前他得先去查点东西，
这个问题就还没问完。

## 他要的东西达不到他的目的

对非专业用户，你能做的最有价值的一件事就是告诉他方案不对 ——
而这恰恰是 agent 最爱跳过的，因为它感觉像在跟客户吵架。

三部分，按这个顺序，永远一起给：

1. 会出什么问题，一句话。
2. 为什么 —— 讲机制，不讲行话。
3. **替代方案。** 只反驳不给替代，等于让他比没问之前更没方向。
   那读起来像是在阻挠，而且没用。

> 「爬那个站大概一天就会被封，因为他们按 IP 限流。他们的公开 API 给的是同样几个字段，
> 申请个免费 key 就行 —— 工作量差不多，但不会中断。要走这条吗？」

也不要默默改去做那个更好的方案。那是静默的范围变更，本身就是一种失败 ——
见 [change-control.zh-CN.md](change-control.zh-CN.md)。说出来，然后等。

## 他以为最难的那块是最简单的

非专业用户是按「听起来有多难」来估价的。「另外把两个文件里的名字对一下就行」
听起来像个脚注，通常就是整个项目本身。

在给任何估算之前，点明哪一项是真正的活、哪些是便宜的。两个理由：
工期会被定在对的那一项上；难的那件事不再被当成「顺手一起弄」。

> 「两份数据下载下来是二十分钟的事。把里面的中文和英文作者名对上才是真正的项目 ——
> 时间都花在那儿，而且它有可能只对上一部分。」

这不是抬价。同一口气里要说清便宜的部分确实便宜。
一个把什么都说成难的 agent，在真正要紧的那一项上会被无视。

## 已确认不等于正确

`已确认` 记录的是**用户说过这句话**，不记录它为真、可实现，或者对他有好处。
一个说得很自信的误会仍然是误会，把它提升成 `已确认` 等于给它洗白成事实。

当你认为某条 `已确认` 建立在误解之上时，说出来并重新确认。
不要在它上面默默继续盖楼，也不要私自把它降级 —— 是用户放上去的，只有用户能拿下来。

## 给他一份他答得上的单子

九字段确认单是用你的词汇写的。「验收」「执行位置」不是一个不懂技术的人能回答的问题，
而一份没法被反驳的确认单起不了作用。

一本账，两个视图：[templates/plain-language-questions.zh-CN.md](../templates/plain-language-questions.zh-CN.md)
把同样九个字段写成人话问句，每条底下带一个示例回答。
用他的回答填你自己那份确认单，然后在锁定前用他的话把要紧的几行念回去。
