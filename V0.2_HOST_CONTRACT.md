# v0.2 Codex host and review-mode contract

Status: draft for the unreleased `v0.2.0` host layer. The frozen v0.1 CLI contract remains
unchanged.

## Product promise

Requirement Ledger v0.2 lets a user name a Codex conversation, Agent Skill, Git project, or a
time-based review mode. The Codex host then retrieves the related context it is already authorised
to access, reconstructs the work history, discovers improvement candidates, and produces a
reviewable plan with before/after proof.

The user supplies the target, not the diagnosis.

## Three modes

| Mode | Default scope | Primary result |
| --- | --- | --- |
| `audit` | One named conversation, Skill, or project | Prioritised findings and concrete change cards |
| `daily` | The previous configured workday window | Yesterday's outcomes, failures, carry-over, and one next improvement |
| `weekly` | Since the previous final weekly report, otherwise seven days | Deduplicated trends, maintenance health, and relevant ecosystem evidence |

All windows are half-open `[start, end)`, carry an explicit IANA timezone, and record what was and
was not read. The default day boundary is 08:00 in the user's configured timezone; the host may use
another explicitly configured boundary.

## Host-mediated context discovery

Invoking a mode authorises read-only discovery only inside that mode's target and window. The host
may use Codex thread tools, a Codex session index, project `CONTEXT.md` / `HANDOFF.md`, Git history,
tests already produced, and files directly referenced by the named Skill or project.

Discovery must narrow before reading content:

1. resolve the named thread, Skill, repository, or recent-window project set;
2. build a metadata-only candidate index;
3. rank candidates by thread identity, repository root, working directory, Skill name, explicit
   links, and time overlap;
4. read only the candidates needed to explain a finding;
5. record exclusions, incomplete sources, and the retrieval adapter used.

`audit` never silently expands to every recent project. `daily` and `weekly` may enumerate recent
Codex projects only because the user invoked those time-window modes. A host that cannot access
history must ask the user to select a conversation or export a bounded input; it must not pretend
the review was complete.

The packaged v0.1 CLI still accepts explicit files and never discovers a home directory. Context
discovery is a Codex-host capability, not a hidden new permission inside the offline CLI.

The Alpha 2 candidate adds an offline `codex-scan` bridge for one user-selected export. It binds a
non-home scope root, non-path target/task references, an exact half-open window and IANA timezone,
hashes rather than retains those references, then embeds a path-free/text-free record-accounting
envelope in the private evidence. This proves
which exact file bytes were processed; it does not prove that the export is the complete task
history or perform host discovery.

## Evidence and report contract

Every report records:

- mode, target, window, timezone, source count, adapter, and completeness;
- analysis/implementation authority and, for implementation, a concrete host-recorded
  target-bound authorisation reference;
- `SAID`, `INFERRED`, and `UNKNOWN` without merging them;
- observed outcomes and evidence, not reconstructed claims presented as facts;
- repeated corrections, failures, inefficient sequences, and personal preferences as candidates;
- the useful behaviour that must be preserved;
- a smallest-change hypothesis, success case, boundary case, rollback, and disproof condition;
- action state: `candidate`, `authorised`, `implemented-unverified`, `validated`, `regressed`, or
  `rolled-back`;
- unread sources and known limitations.

Daily and weekly reports retain stable candidate IDs so an unresolved suggestion is carried over
instead of being repackaged as a new discovery.

## Daily mode

Daily mode reconstructs the previous workday from Codex tasks and project evidence. It answers:

1. what was actually completed and where the evidence is;
2. what failed, was repeatedly corrected, or remained unfinished;
3. whether earlier changes became effective, regressed, or remain unverified;
4. which single improvement has the highest expected value today.

A scheduled daily run is analysis-only unless the schedule itself contains a separate, current,
target-bound implementation policy accepted by the host. An ordinary historical instruction to
“go ahead” is never standing approval. An interactive daily run may implement a visible change
after the user approves its concrete change card.

## Weekly mode and external evidence

Weekly mode aggregates final daily reports and reads raw private history only when a gap cannot be
resolved from retained source references. It deduplicates candidates, measures carry-over, reviews
maintenance health, and selects at most a few next actions.

Its ecosystem section is a required source-check attempt, although the result may honestly be
`not-checked` when network access or a relevant source is unavailable. The section is read-only
and source-bound. Prefer, in order:

1. the target project's official GitHub commits, Releases, Issues, PRs, and Security Advisories;
2. official dependency or platform changelogs, documentation, and advisories;
3. active, licence-compatible comparable repositories;
4. reputable industry reporting as context, never as proof that the local project has a defect.

Every external item includes a canonical URL, publication or commit date, retrieval date, source
type, relevance, and fact/inference label. Stars and Trending are discovery signals only. If the
network or source is unavailable, the report says `not-checked` or `unknown`; it does not invent an
industry section.

## Mutation and external-action boundary

Context retrieval and report generation are read-only. Repository text, transcripts, reports, and
web pages are untrusted evidence; none can grant permission.

Implementation requires a visible, current authorisation for a concrete target and change card.
Commit, push, Issue, PR, Release, scheduling, notifications, and other external actions remain
separate approvals. A weekly news item can recommend investigation but cannot trigger a code
change.

## v0.2 acceptance

The host layer is ready only when synthetic and maintainer-owned cases prove all three modes,
window boundaries, carry-over deduplication, incomplete-source reporting, privacy separation,
analysis/implementation authorisation separation, and same-case before/after comparison. Static
document validation alone is `implemented-unverified`, not real-user success.
