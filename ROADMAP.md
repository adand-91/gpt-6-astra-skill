# Roadmap

Requirement Ledger AI is moving from a released evidence prototype to a focused `v1.0.0`
launch. Dates are targets, not permission to ship unfinished or fabricated activity. Every public
version must represent a coherent, tested capability.

## Product destination

`v1.0.0` is a stable AI project and Skill feedback loop:

```text
explicit conversation + Git/test evidence
  -> private, traceable findings
  -> daily/weekly or Skill-specific improvement report
  -> reviewed host-owned Codex change
  -> same-oracle before/after evidence
```

The CLI remains the evidence layer. It does not silently discover private histories, run project
code, edit a worktree, or perform GitHub/account actions.

## Fifteen-day launch track

### `v0.1.1` — discovery and first use

- Clear Requirement Ledger AI positioning and search metadata.
- A five-minute install path and sixty-second synthetic product tour.
- A reproducible, anonymous Skill-improvement walkthrough.
- English normative documentation with a maintained Chinese mirror.

Exit gate: a new user can explain the product boundary and reproduce the walkthrough without
private data or undocumented steps.

### `v0.2.0` — reports and project rhythm

- Daily improvement report from an explicit evidence window.
- Weekly project and ecosystem report.
- Human-confirmed grouping of related corrections.
- A small first set of structured test-log adapters.

Exit gate: the reports produce one actionable next step on real maintainer-owned projects without
turning incomplete evidence into confirmed attribution.

### `v1.0.0-rc.1` — complete launch candidate

- A documented Requirement Ledger → Codex → Skill-maintenance handoff.
- Stable CLI and schema for the promised v1 workflow.
- Clean installation, deterministic Demo, privacy gates, and cross-platform CI.
- Launch assets, real maintainer-owned case evidence, limitations, and migration notes.

Exit gate: every v1 promise passes the release checklist on the same commit. Any failed gate stops
the final release.

### `v1.0.0` — public launch

The release candidate becomes `v1.0.0` only when its code, documentation, examples, packages, and
public CI agree. `1.0` means a stable product promise, not autonomous editing or perfect diagnosis.

## After launch

- `1.0.x`: compatible bug, privacy, parser, packaging, and documentation fixes backed by evidence.
- `1.1.0`: compatible new adapters, reports, and workflows.
- `2.0.0`: only for a deliberately incompatible contract or a proven controlled-intervention
  architecture.

There is no fixed patch-release count. Real Issues, reproductions, security needs, and coherent
features drive releases; a no-change period creates no Git noise.

## Explicitly outside the v1 launch

- Unattended code or Skill modification.
- Automatic commit, push, Issue, PR, Release, upload, or telemetry.
- A web account system, hosted dashboard, or team permissions.
- Claims that a pattern-based privacy check makes an artefact safe to share.
- A general-purpose sandbox, transactional apply, or automatic rollback engine.
